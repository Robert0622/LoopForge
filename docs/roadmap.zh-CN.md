# 规划

[English](roadmap.md)

LoopForge 的目标是需求的全自动 Loop：一张需求进来，一个可合并的 Pull Request 出去，人只在团队认为必须介入的地方出现。本页列出规划中的方向。它不是排期，优先级会根据反馈调整，欢迎提 Issue 和 Pull Request。

## 已经具备

- **自动 Loop**：Issue 定时同步、澄清打分、定时派发、明确结论与命令门禁、打回重做并重置下游、集成分支与 PR 交付、可选的人工审批节点。
- **逐次运行隔离**：每次运行一个容器，`docker compose` 部署开箱即用，绑定的执行机器或任何装有 Docker 的主机同样支持。
- **可观测与可评测**：每次运行的实时遥测、跨运行的流程指标，以及每次运行的评测；评测建议可以一键应用到 SOP 和角色上。
- **专家经验沉淀为 SOP**：内置后端、前端、产品交付 SOP，可复用的角色，带完整尝试历史的声明式产物，通过 MCP 检索知识库。

## 规划中

### 自反馈闭环

评测已经能针对 SOP 节点、门禁和角色指令提出具体修改，目前由人来应用。接下来：

- 跨运行汇总建议，把反复出现的问题挑出来，而不是一次只看一个运行。
- 低风险的修改自动生成新的 SOP 或角色版本，附上依据，并支持一键回滚。
- 对比修改前后的指标（一次通过率、返工率、交付耗时），由闭环自己决定保留还是回退。

### 对话式入口

工作总览已提供对话入口：一句话澄清、建单开跑，并能看到正在运行和待确认的工作流。后续会接到更多聊天工具，并把结果以回复形式返回（PR、预览或报告）。完整的工作台依然保留，用来配置 SOP 和角色。

### 更快跑通第一张需求

- 在完整交付模板之外，提供一条短的「快速修复」SOP（实现 → 测试 → 提 PR）。
- 更精简的 Studio 导航：先展示日常用的视图，把配置项收起来。
- 英文界面。

### 不依赖 Docker socket 的隔离

默认部署已经做到每次运行一个容器，但依赖宿主机的 Docker socket，等同于这台主机的 root 权限。规划：提供 rootless 方案（例如 rootless Docker 或专门的沙箱运行时），在保留逐次容器隔离的同时，不把宿主机交给平台。

### 减少依赖

- SOP 运行之外的 AI 功能（需求澄清、AI 助手、运行评测）目前使用 CodeBuddy，规划支持任意已配置的执行器或模型服务。
- 支持更多执行器，包括 ACP 兼容的 Agent。
- 支持更多需求系统：GitLab、Gitea、Jira，通过 [extending.md](extending.md#issue-trackers) 中的 Provider 接口实现。
- 产物支持对象存储后端。

## 参与规划

较大的改动请先开 Issue 讨论；小的改进可以直接提 Pull Request，见 [CONTRIBUTING.md](../CONTRIBUTING.md)。
